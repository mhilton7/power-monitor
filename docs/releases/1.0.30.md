# Power Monitor Server 1.0.30

## Release identity

- Server version: `1.0.30`
- Alembic head: `20260803_0030`
- Device protocol: `pm-protocol/1.0.0` (unchanged)
- Source commit: recorded by the clean release build
- Published image digests: recorded after GHCR publication

Version `1.0.30` is reserved for the coordinated stability, History, and OTA
hardening release. It must not be reused for different source or image bytes.
Production builds inject `POWER_MONITOR_VERSION=1.0.30` from the immutable
image tag; development defaults remain `1.0.0` and are not release identity.

## Included changes

- Exact PostgreSQL History aggregation and pagination avoid hydrating the
  unbounded raw-reading set while preserving Decimal rate and tier results.
- History measurement and pricing queries share a repeatable-read snapshot,
  with a bounded auxiliary connection and a serial fallback under pool
  pressure.
- The browser History client coalesces refreshes, cancels superseded requests,
  and keeps large accessible tables out of the DOM until requested.
- Firmware deployment transitions are centralized, idempotent, and reconciled
  by the worker rather than relying on an administrator opening the page.
- OTA evidence ordering rejects stale reports and preserves authenticated,
  monotonic progress for each deployment attempt.
- The release workflow binds dependency audits, migration evidence, source
  commit, toolchain versions, and image metadata before publication.

## Database migrations

The release advances from `20260803_0027` through these append-only revisions:

1. `20260803_0028` -- OTA lifecycle terminalization and reconciliation indexes.
2. `20260803_0029` -- coarse History query indexes.
3. `20260803_0030` -- authenticated OTA update-window waiting state.

The canonical offline migration artifact is generated by
`scripts/generate_release_reports.py`; raw Alembic offline rendering is not a
supported release artifact because an older immutable data-dependent revision
requires the repository compatibility renderer.

## Measured validation

- PostgreSQL 17.5 exact tiered History warm p95: 0.1643 seconds for seven days
  and 0.4104 seconds for 30 days.
- Same-build raw-reference reductions: 87.01% and 94.46% respectively.
- Required 8-sensor/30-day and 1-sensor/366-day matrices complete at 0.7166
  and 0.6524 seconds warm p95.
- Compound signed-protocol load: 72/72 HTTP requests succeeded; endpoint p95
  remained at or below 0.6337 seconds with zero pool failures or starvation.
- Logical backup was checksummed, restored into a clean PostgreSQL database,
  and verified at Alembic head with all seeded devices and readings.

Detailed measurements are retained in

## Deployment and rollback

Publish the API, frontend, and backup images under the single version
`1.0.30`, record their immutable digests, then render and validate the TrueNAS
YAML. The PostgreSQL host path remains exactly:

```yaml
volumes:
  - /mnt/Apps/Power/postgres:/var/lib/postgresql/data
```

Before upgrade, create the verified logical backup and TrueNAS ZFS snapshot
described in the deployment documentation. Rollback restores the prior
digest-pinned application images; if database rollback is required, restore
the pre-upgrade logical backup or ZFS snapshot using the documented procedure.

## Final release gates

The clean release build must fill in the source commit and published image
digests above and must not mark this release complete until the full automated
matrix, isolated seven-service Compose deployment, backup/restore verification,
and applicable physical sensor canary gates have passed. A hardware-blocked
canary is reported as an external blocker, not as a successful production
release.
