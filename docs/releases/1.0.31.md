# Power Monitor Server 1.0.31

## Release identity

- Server version: `1.0.31`
- Alembic head: `20260803_0030`
- Device protocol: `pm-protocol/1.0.0` (unchanged)
- Source commit and archive SHA-256: generated and verified by the clean release
  workflow in `release/versions.json` and `release/checksums.sha256`
- GHCR digests: intentionally unpublished until the exact sensor 1.0.16
  physical canary passes

Version `1.0.31` supersedes the unpublished 1.0.30 candidate because that
archive carried an outdated 1.0.29 release-notes heading. The earlier bytes are
not overwritten or reused under this version.

## Included changes

- Exact metric-aware PostgreSQL History aggregation, repeatable-read pricing
  snapshots, signed continuation pages, and bounded concurrency.
- Route-scoped, abortable History requests with SSE burst coalescing and a
  bounded accessible/chart DOM.
- Worker-driven, monotonic, idempotent OTA lifecycle reconciliation with
  attempt isolation and explicit expiry/rollback outcomes.
- Hardened source-frozen release archives whose verifier checks embedded
  provenance, inventories, migrations, lockfiles, OTA artifacts, protocol, and
  duplicate or unverified members.
- Makes source archives cross-platform deterministic by disabling checkout
  line-ending conversion for `git archive`, and generates and verifies every
  committed source-evidence hash from the frozen Git blob rather than the
  filtered worktree; embedded source hashes therefore bind to identical bytes
  on Windows and Linux.
- Bounds the Windows Playwright release matrix to two workers after an
  instrumented run proved that four concurrent browser contexts could exhaust
  local socket buffers and fail a valid production asset request.
- Coordinated canary-only sensor 1.0.16 memory and fail-closed OTA changes; no
  firmware is promoted stable by this server candidate.

## Database migrations

The release advances through append-only revisions `20260803_0028`,
`20260803_0029`, and `20260803_0030` for OTA terminalization, coarse History
indexes, and the authenticated waiting-for-schedule state.

## Measured validation

- Exact tier/cost History warm p95: 0.1643 seconds for seven days and 0.4104
  seconds for 30 days, reductions of 87.01% and 94.46% versus the retained raw
  reference.
- Compound signed-protocol load: 72/72 requests returned HTTP 200 with no pool
  failure or endpoint starvation; encrypted logical backup and clean restore
  passed.
- Frontend production trace: 720 points in 500+220 pages, 25 reading events
  coalesced into one refresh, 221 DOM nodes, and zero Long Tasks.
- Sensor automation: 102 Python tests, 128 randomized sanitizer sequences with
  14,080 events, 36 Web UI tests, and 12 browser tests.

## Deployment and rollback

The PostgreSQL host path remains exactly:

```yaml
volumes:
  - /mnt/Apps/Power/postgres:/var/lib/postgresql/data
```

After the physical canary, publish the API, frontend, and backup images under
one immutable `1.0.31` version with digest pins, render the TrueNAS YAML, and
repeat the isolated deployment/restore gate. Before upgrade, create the
verified logical backup and TrueNAS ZFS snapshot. Server rollback uses the
prior digest-pinned images plus the pre-upgrade backup or snapshot if database
restoration is required.

The server candidate may be archived and verified before the sensor canary,
but Git push, tag, GHCR publication, and production-YAML promotion remain
deferred while the hardware gate is pending.
